# PRD: EVDI 云桌面平台 V1

## 1. Summary

本文档定义 EVDI 云桌面平台 V1 的整体产品需求。EVDI 是一款面向企业的商业云桌面产品，正在从现有架构升级到基于 K8s+KubeVirt+WebRTC 的云原生架构。V1 的核心目标是：通过 WebRTC 实现浏览器零安装访问远程桌面（零客户端），同时通过 Tauri 原生客户端提供 USB 重定向、多显示器等专业能力。产品覆盖七层架构中的 L1（客户端）至 L4（桌面交付），基于开源组件构建，闭源商业化。

## 3. Background

### 3.1 产品现状

EVDI 是已有付费客户的商业云桌面产品。当前产品基于传统虚拟化架构，依赖专用客户端，存在以下问题：

- **客户端部署重**：每个终端需要安装专用客户端，IT 推送更新成本高，出差/临时访问困难
- **架构扩展性不足**：现有架构无法低成本横向扩展，大规模部署（500+席位）运维成本高
- **技术栈封闭**：私有协议难以定制，客户二开需求无法满足

### 3.2 为什么做架构升级

架构升级的核心驱动力是两个已被客户验证的需求：

1. **零客户端能力**：客户强烈要求浏览器直接访问远程桌面，免去客户端安装。现有架构基于私有协议，无法支持浏览器访问
2. **规模扩展与运维降本**：现有架构在 500+ 席位时运维成本显著上升，需要云原生化实现自动化运维

### 3.3 为什么是现在

- **WebRTC 成熟**：Pion WebRTC v4 趋于稳定，MVP 已验证视频+输入基本链路
- **K8s 生态完备**：KubeVirt 1.x 稳定，Longhorn/Kube-OVN 生产就绪
- **市场窗口**：Broadcom 收购 VMware 后客户重新评估方案，国产替代需求增强
- **Tauri v2**：原生客户端能力（系统 Hook、USB）比 v1 更成熟

### 3.4 有什么新变化

- MVP 已验证：Pion WebRTC + GStreamer 编码链路可行，浏览器可以看到桌面并操作
- 发现 DataChannel Lite ICE 单向性问题，已有 WebSocket 回退方案
- 客户对零客户端需求持续增强，已成为续约和拓客的关键因素

## 4. Objective

### 4.1 核心目标

**通过云原生架构升级，让 EVDI 成为国内首个"浏览器即桌面"的企业级云桌面产品——用户 5 秒内从浏览器进入远程桌面，重度用户通过 <15MB 原生客户端获得专业级体验，运维成本随规模线性增长而非指数增长。**

### 4.2 关键结果（OKR）

| # | 关键结果 | 目标值 | 衡量方式 |
|---|----------|--------|----------|
| KR1 | 零客户端连接成功率 | ≥95% | 浏览器成功建立 WebRTC 连接 / 尝试连接 |
| KR2 | 零客户端端到端操作延迟 | <150ms（局域网） | 键鼠输入到屏幕响应的时间差 |
| KR3 | 弱网场景体验与竞品差距 | ≤20% | 跨运营商/2%丢包场景下延迟差距 |
| KR4 | 首次使用到进入桌面时间 | <60 秒 | 从打开浏览器到看到桌面画面的时间 |
| KR5 | 断线重连成功率 | ≥90% 在 5 秒内 | 网络波动后自动恢复连接的比例 |
| KR6 | 500 席位部署运维人力 | ≤2 人 | 运维团队规模 / 管理席位数 |
| KR7 | 桌面实例启动时间（冷启动） | <90 秒 | 从点击启动到 Ready 状态 |
| KR8 | Web→Tauri 升级转化率 | ≥20% | 安装 Tauri 的 Web 用户占比 |

### 4.3 战略对齐

| 战略维度 | V1 定位 |
|----------|---------|
| **差异化** | 零客户端（浏览器直接访问）—— 深信服/华为/锐捷均不支持 |
| **市场定位** | 企业级云桌面，从中型客户（50-500 席位）切入 |
| **商业模式** | 闭源商业授权，按席位/资源计费 |
| **技术护城河** | WebRTC 体验优化 + K8s 云原生运维能力 + 安全合规策略引擎 |

### 5.3 市场约束

| 约束 | 说明 |
|------|------|
| 中国企业网络环境 | 跨运营商（电信↔联通↔移动）延迟高、丢包率高，WebRTC 需做弱网优化 |
| 企业安全策略 | 严格 IT 管控可能阻断 WebRTC 端口、禁止浏览器访问外网 |
| Windows 桌面依赖 | 大量企业依赖 Windows 生态，Windows VM 支持是刚需 |
| 国产化替代 | 政企客户要求国产化适配（麒麟/统信 + 海光/鲲鹏） |

## 7. Solution

### 7.1 UX / 用户流程

#### 7.1.1 终端用户主流程

```
用户打开浏览器/启动 Tauri
    │
    ▼
登录页（JWT 认证 / SSO）
    │
    ▼
桌面列表页
    │  显示可用桌面、运行状态、最近连接
    │  首次使用：3 步引导
    │
    ▼ 选择桌面 → 点击"连接"
    │
    ▼
连接中（占位画面 + 进度提示）
    │  获取 TURN 凭证 → WebSocket 信令 → SDP 协商 → ICE → 媒体流
    │  超时/失败：显示错误 + 重试按钮
    │
    ▼
远程桌面（全屏模式）
    │  Canvas/wgpu 渲染视频流 + 键鼠输入
    │  边缘触发浮动工具栏
    │  网络波动 → 占位画面 → 自动重连
    │
    ▼ 关闭/断开
    │
    ▼
桌面列表页（返回）
```

| D6 | 多租户网络隔离 | P0 | Kube-OVN Subnet + ACL | 租户间网络完全隔离 |

### 7.3 Technology

#### 7.3.1 七层架构

```
┌──────────────────────────────────────────────────────┐
│ L1  客户端层       Web 客户端 · Tauri Native 客户端    │
├──────────────────────────────────────────────────────┤
│ L2  媒体与接入层   Coturn · Pion WebRTC · GStreamer   │
├──────────────────────────────────────────────────────┤
│ L3  业务编排层     云桌面控制台 · Broker（6 子服务）    │
├──────────────────────────────────────────────────────┤
│ L4  云桌面交付层   Linux 容器 Pod · Windows VM         │
├──────────────────────────────────────────────────────┤
│ L5  K8s 工作负载   KubeVirt · Longhorn · Kube-OVN     │
│                    · Prometheus Operator · Grafana     │
├──────────────────────────────────────────────────────┤
│ L6  K8s 编排层     Kubernetes 控制面                   │
├──────────────────────────────────────────────────────┤
│ L7  基础设施层     物理服务器 · 物理网络 · 物理存储     │
└──────────────────────────────────────────────────────┘
```

#### 7.3.2 核心技术选型

| 组件 | 选型 | 协议 | 选型理由 |
|------|------|------|----------|
| 编排 | Kubernetes + KubeVirt | Apache-2.0 | 统一调度 Linux 容器与 Windows VM |
| 存储 | Longhorn | Apache-2.0 | 3 副本强一致，数据本地化读 |
| 网络 | Kube-OVN | Apache-2.0 | VLAN 桥接企业内网，多租户隔离 |
| 信令穿透 | Coturn | BSD-3-Clause | STUN/TURN/NAT 穿透 |
| 媒体传输 | Pion WebRTC | MIT | Go 原生，MIT 可闭源 |
| 编解码 | GStreamer | LGPL-2.1 | 跨 GPU 硬编码，进程隔离合规 |
| 客户端 | Tauri (Rust) | MIT/Apache-2.0 | <15MB，Rust 系统级能力 |
| 消息总线 | NATS JetStream | Apache-2.0 | 轻量级异步通信 |
| 数据库 | PostgreSQL | PostgreSQL License | 业务数据，审计按月分区 |
| 缓存 | Redis | BSD-3-Clause | WS 多副本同步、Token 黑名单 |

#### 7.3.3 数据流

```
用户 → 浏览器/Tauri
         ↓ HTTPS/WSS
       Ingress（TLS 终结）
         ↓
       Broker Gateway（信令编排）
         ↓ WebSocket 信令
       Agent（桌面实例内）
         ↓ Pion WebRTC
       用户（媒体流 P2P / TURN 中转）
```

- **信令流**：Client ↔ Broker Gateway ↔ Agent（WebSocket，经 Ingress）
- **媒体流**：Client ↔ Agent（WebRTC，P2P 优先，TURN 中转兜底）
- **控制流**：Client ↔ Broker Desktop Service（REST API，经 Ingress）

### 7.4 Assumptions

| # | 假设 | 信心度 | 验证方式 | 失败影响 |
|---|------|--------|----------|----------|
| AS-1 | 零客户端是客户选择 EVDI 的首要决策因素 | 55% | 发现计划 G2：客户深度访谈 | 需要找其他核心差异化点 |
| AS-2 | WebRTC 弱网体验不低于竞品私有协议 | 45% | 发现计划 G1：对比盲测 | 需要混合协议方案或弱网优化 |
| AS-3 | 高级功能（USB/多屏）缺失会让 Web 用户流失 | 50% | 发现计划 G3：功能边界分析 | Tauri 投入需调整 |
| AS-4 | 深信服/锐捷客户会因零客户端切换到 EVDI | 40% | 发现计划 G2：竞品客户访谈 | 市场策略需调整 |
| AS-5 | EVDI TCO 低于深信服/华为 | 45% | 发现计划 G4：竞品 TCO 对标 | 定价策略需调整 |
| AS-6 | KubeVirt 生产环境足够稳定 | 50% | V1 试运行期验证 | Windows VM 场景需要备选方案 |
| AS-7 | Pion DataChannel 双向通信在 Full ICE 下可修复 | 55% | 技术验证 | 输入保持 WebSocket 回退 |
| AS-8 | GStreamer 进程隔离满足 LGPL 合规 | 80% | 法律顾问确认 | 需要调整隔离方案 |
| AS-9 | Tauri+wgpu 渲染性能优于 Canvas | 50% | 技术验证 | Tauri 回退 Canvas 渲染 |
| AS-10 | 500 席位运维人力可控制在 2 人 | 50% | V1 试运行期验证 | 运维自动化投入需加大 |

## 附录 A：名词解释

| 术语 | 含义 |
|------|------|
| 零客户端 | 通过浏览器直接访问远程桌面，无需安装任何软件 |
| WebRTC | Web Real-Time Communication，浏览器原生支持的实时通信协议 |
| Pion | Go 语言实现的 WebRTC 库，MIT 协议 |
| GStreamer | 跨平台多媒体框架，支持多种硬件编码 |
| KubeVirt | Kubernetes 虚拟化扩展，在 K8s 上运行 VM |
| Longhorn | K8s 原生分布式块存储 |
| Kube-OVN | 基于 OVS 的 Kubernetes 网络插件 |
| Tauri | Rust 桌面应用框架，替代 Electron |
| DataChannel | WebRTC 数据通道，用于传输键鼠/剪贴板等控制数据 |
| TURN | Traversal Using Relays around NAT，NAT 穿透中继服务器 |
| Broker | EVDI 业务控制平面，管理桌面/会话/调度/信令 |
| Agent | 运行在桌面实例内的媒体+输入引擎 |
| Kagent | AI 运维 Agent，用于告警分析和自动修复 |
